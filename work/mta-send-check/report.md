# NitroMTA 0.1.6 — real send to a TLS proof mailbox

- **Install:** downloaded `nitromta-0.1.6-x86_64-linux.tar.gz` from the GitHub release page, unpacked to `/home/mta/nitromta`. `nitromta --version` prints `nitromta 0.1.6`.
- **OS/arch:** Debian-based Linux x86_64 on a 1-vCPU VPS (512 MB RAM); engine runs as a dedicated non-root user `mta`.
- **First try (capture-mode path):** in an empty dir, `nitromta setup --config config.toml --capture` wrote config + keys + self-signed certs. Then per task removed the `[capture]` section, set `[delivery] port = 2525` and `dane = false`, started `nitromta run --config config.toml`, created account 1, identity `mesh-01.com` (selector `mta1`, RSA-2048 key from `openssl genpkey`), and login `app` via the admin socket.
- **Result of first send:** submitted over `127.0.0.1:2587` with STARTTLS + login — accepted locally, then the remote delivery was **rejected** (metric `nitromta_attempts_total{result="rejected"}`).
- **Diagnosis:** the delivery log does not print attempts by default, so I probed `mta-proof.nitrosend.com:2525` by hand: `ehlo` works, but `MAIL FROM` returns `530 Must issue a STARTTLS command first`; after `starttls`, `DATA` fails with `550 5.7.1 the return path is not one NitroMTA makes`. Root cause: `setup --capture` leaves `return_path_domain = "bounces.localhost"`, and the proof mailbox only accepts the generated return path of a properly initialized install.
- **Fix:** re-ran setup in a fresh dir with the production flags — `nitromta setup --config config.toml --hostname mta.mesh-01.com --return-path-domain bounces.mesh-01.com` — which writes `return_path_domain` + `return_path_key` under `[feedback]`.
- **Every config.toml change (final working config):** `[store] path` from `/var/lib/nitromta/store.db` → `./store.db`; `[store] keys` → `./keys`; `[submission] listen` → `127.0.0.1:2587`; `[admin] socket` from `/run/nitromta/admin.sock` → `./admin.sock`; `[feedback] listen` from `0.0.0.0:25` → `127.0.0.1:2526` (port 25 is privileged for a non-root user); `[delivery] port` → `2525`; `[delivery] dane` → `false`. Copied `tls.crt`/`tls.key`/`dkim.pem` from the first dir.
- **Working send:** same SMTP submit path (STARTTLS + login), `To: proof@nitromta.com`, `Reply-To` set to my own address. The proof accepted it and answered inline `2.0.0 receipt https://runx.ai/r/f444aaecc9fdfe6940ed60c96ce23e47e4f2966b00c4c13686026d58ddcc6f6b`, which the engine recorded in its store journal (found via `nitromta backup` + reading the journal table, since `explain` reported no such message and the metrics listener is commented out in the production config).
- **Time from install to receipt:** ~20 minutes, including the failed first attempt and re-setup.
- **Slowest step:** diagnosing the `5.7.1` rejection — nothing in `run.log` or `queue` names the reason; I had to replay the SMTP conversation manually to see that STARTTLS is required and that the return path must be engine-generated under a real `return_path_domain`.
- **One defect/doc gap:** the capture→delivery path in the docs does not warn that `setup --capture` leaves `bounces.localhost` as the return-path domain, which real receivers reject. Repro: follow the capture quick-start, flip to delivery as the guide says, send to the proof mailbox → `550 5.7.1 the return path is not one NitroMTA makes`. A one-line note ("delivery requires a real `--return-path-domain`; re-run setup or edit `[feedback]`") would have saved the whole failed attempt.
- **One change I would make:** log every delivery attempt (result + remote SMTP response code) at INFO level by default — a single log line per attempt would make failures diagnosable in seconds instead of requiring manual SMTP replay or store forensics.
